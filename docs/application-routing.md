# Application routing contract

Android owns VPN application capture through `VpnService.Builder` allow/exclude lists. Imported profiles cannot provide those lists or runtime policy. Validated app-owned settings choose Whole device or Proxy; the owner package remains in an include list so connection validation stays VPN-bound. An empty selected VPN list captures only the owner instead of silently capturing every application. This path works on the application's Android 7/API 24 minimum.

Website rules apply within the captured applications. An exact hostname (`example.com` or `full:example.com`) selects that host. A suffix (`*.example.com`, `.example.com`, `+.example.com`, `domain:example.com` or `suffix:example.com`) includes the hostname and its subdomains. Zones such as `ru`, `.ru`, `*.ru` and `zone:ru` share one canonical suffix rule; international names use their ASCII IDN representation. HTTP/HTTPS URLs and addresses with a path or port select the entire hostname, so URL paths and ports are not separate routing criteria. The input sheet displays the canonical rule before saving.

Proxy-profile domain rules use Core fake-IP name bindings while retaining the profile’s exact advertised resolver, upstreams and DNS egress. Inferred names from real-IP answers can restrict an IP route, so they cannot authorize Direct bypass. Numeric rules retain their original DNS mode. WireGuard keeps the profile's raw private resolver and declares its address through Core's `dns.packet_resolvers` contract. WireGuard domain routing requires Android 10/API 29 or newer for platform UID attribution, and a paired DNS answer received through the authenticated tunnel. UDP and TCP DNS are supported; agreeing explicit domain rules can authorize Direct, while ambiguous names, missing attribution or expired/unbound answers cannot. A shared real address cannot distinguish an unqueried name or reveal encrypted DNS; proxy profiles use fake-IP bindings for that separation.

Numeric IPv4/IPv6 addresses, CIDR networks and inclusive address ranges use native network matchers. Ranges must have ordered endpoints in one address family and expand into bounded CIDR groups. VPN, Direct and Block all use the same validated destination representation. Invalid or noncanonical masks are rejected before native policy installation; saved rule and expanded native rule counts remain bounded at 4,096.

Direct applications are excluded from the normal VPN TUN. Their data and DNS use Android's physical-network routing and resolver namespace, including the system Private DNS policy. Captured VPN applications keep the validated profile's DNS policy, including raw private WireGuard DNS. No per-package DNS result is selected by guessing an Android system-resolver UID, and no public resolver fallback is introduced.

An effective live routing change first arms the current native kill switch and establishes a separate, unread all-application IPv4/IPv6 TUN with blackhole DNS. Only after that descriptor is owned may the previous native session and master descriptor close. Settings are then saved under the existing command-generation and secure-store transaction fence. A stopped VPN is never started by preference edits.

After settings commit, a target TUN is established with the new Android application lists and original profile DNS. This successful establish is the OS routing commit: newly Direct applications can use the physical network at that point. It deactivates the previous blackhole interface even if its descriptor remains open. The target native session starts blocked, then releases its native hold and completes the bounded VPN-bound proof before the app publishes Connected.

A target startup/proof failure must establish a new full barrier before closing the target. If re-establishment fails, the existing target capture is retained rather than closed into an uncontrolled fallback. The app does not automatically kill the process on a failed policy handover. A failed native stop retains its owner for explicit Stop; descriptors belonging to a late completion cannot be adopted into a superseding generation. Temporary interfaces are never adopted by Core, so their queued packets cannot replay.

Logical session ownership is separate from each physical TUN/native frame. Stop invalidates that owner, releases the gate and target frames, drains late starts within a bounded budget and restores normal Android networking. A reused NetworkAgent is accepted through current ownership, not inferred from a new/disappearing handle. Android 30+ still requires the VPN owner UID; Android 24–29 handovers additionally require a fresh successful owned descriptor and current VPN permission.

Core's kill-switch falling edge revokes decisions cached while blocked. This avoids the former WireGuard same-flow hold without simulating a network change or forcing continuity overrides. DNS response caches retain one total capacity and separate attributed identities, egress lane and epoch; fake-IP promises are not withdrawn. This does not claim to repair arbitrary cached addresses created by another VPN or implement new DNS filtering behavior in Guard.

The barrier covers traffic captured by this Android VPN. Protected transport/control sockets, permission revocation, replacement by another VPN and process death remain platform lifecycle boundaries. App-side handover is not Android always-on VPN lockdown. The existing confirmation preferences select the existing confirmation UI; their default and saved choices do not remove the traffic barrier.
