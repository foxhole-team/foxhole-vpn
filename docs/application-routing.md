# Application routing contract

Android owns VPN application capture through `VpnService.Builder` allow/exclude lists. Imported profiles cannot provide those lists or runtime policy. Validated app-owned settings choose Whole device or Proxy; the owner package remains in an include list so connection validation stays VPN-bound. An empty selected VPN list captures only the owner instead of silently capturing every application. This path works on the application's Android 8/API 26 minimum.

Direct applications are excluded from the normal VPN TUN. Their data and DNS use Android's physical-network routing and resolver namespace, including the system Private DNS policy. Captured VPN applications keep the validated profile's DNS policy, including raw private WireGuard DNS. No per-package DNS result is selected by guessing an Android system-resolver UID, and no public resolver fallback is introduced.

An effective live routing change first arms the current native kill switch and establishes a separate, unread all-application IPv4/IPv6 TUN with blackhole DNS. Only after that descriptor is owned may the previous native session and master descriptor close. Settings are then saved under the existing command-generation and secure-store transaction fence. A stopped VPN is never started by preference edits.

After settings commit, a target TUN is established with the new Android application lists and original profile DNS. This successful establish is the OS routing commit: newly Direct applications can use the physical network at that point. It deactivates the previous blackhole interface even if its descriptor remains open. The target native session starts blocked, then releases its native hold and completes the bounded VPN-bound proof before the app publishes Connected.

A target startup/proof failure must establish a new full barrier before closing the target. If re-establishment fails, the existing target capture is retained rather than closed into an uncontrolled fallback. The app does not automatically kill the process on a failed policy handover. A failed native stop retains its owner for explicit Stop; descriptors belonging to a late completion cannot be adopted into a superseding generation. Temporary interfaces are never adopted by Core, so their queued packets cannot replay.

Logical session ownership is separate from each physical TUN/native frame. Stop invalidates that owner, releases the gate and target frames, drains late starts within a bounded budget and restores normal Android networking. A reused NetworkAgent is accepted through current ownership, not inferred from a new/disappearing handle. Android 30+ still requires the VPN owner UID; Android 26–29 handovers additionally require a fresh successful owned descriptor and current VPN permission.

Core's kill-switch falling edge revokes decisions cached while blocked. This avoids the former WireGuard same-flow hold without simulating a network change or forcing continuity overrides. DNS response caches retain one total capacity and separate attributed identities, egress lane and epoch; fake-IP promises are not withdrawn. This does not claim to repair arbitrary cached addresses created by another VPN or implement new DNS filtering behavior in Guard.

The barrier covers traffic captured by this Android VPN. Protected transport/control sockets, permission revocation, replacement by another VPN and process death remain platform lifecycle boundaries. App-side handover is not Android always-on VPN lockdown. The existing confirmation preferences select the existing confirmation UI; their default and saved choices do not remove the traffic barrier.
